# デモ報告書 — 架空の重要業務クラウド復旧環境

**すべて架空。実在の金融機関、顧客、社内案件の構成を表したものではありません。構築・復元・侵害試験は実施していません。**

対象ツール: CleanRoomCheck 0.1.0a1 / ルール2026.10-alpha1 / 評価日2026-10-14。

## 目的

「別サブスクリプションにした」「バックアップを不変化した」という個別説明を、テナント侵害を想定した分離設計・復旧可否・未検証事項の整理につなげるデモです。製品の選定や実導入の有効性を実証するものではありません。

## 仮定した環境

Azure上の重要業務VMを1業務とし、本番用と復旧用のサブスクリプション、バックアップ保管先、カスタマー管理の復号鍵、共通CI/CDなどをモデル化します。Entraテナント全体管理者、バックアップ管理者、共通CI/CDの3侵害シナリオを設定します。

不備例では本番・復旧が同一テナントに所属し、復旧用端末の独立性や承認分離が未成立です。不変性は解除可能な状態を仮定し、必要保持期間に不足する保持日数、本番側からの鍵破壊権限、許可された復旧側への通信などを入力しています。細かな値と方向は `examples/azure-risky.json` が正本です。

証跡IDは架空の構成確認メタデータを表します。実ファイルやクラウド設定から取得したものではありません。実施していない復号・復元・検証試験はnullのままです。

## 点検結果

| 判定 | 不備のある構成 | 改善設計案 |
|---|---:|---:|
| 不成立 | 35 | 0 |
| 情報不足 | 36 | 39 |
| 成立（モデル上） | 13 | 45 |
| 対象外 | 12 | 12 |
| 合計 | 96 | 96 |

1業務×3シナリオ×32ルールで96点検です。同じ設定不備が複数の侵害シナリオに該当するため、35個の独立した脆弱性があるという意味ではありません。M365の4ルールはAzure VM例のため3シナリオで計12点検が対象外です。

## 改善設計の仮定

復旧先のテナントと管理権限を分け、独立端末・承認経路を用意し、本番側からの管理/破壊/通信経路を除いたと仮定します。バックアップの確定した不変性、保護適用と期限、業務の保持要件への対応を入力します。対応範囲を示す架空の構成確認メタデータを紐付けます。

ただし、復旧先を別テナントにすると標準Azure VM復元の同一テナント制約を考慮する必要があります。改善案では方式をvendorとし、製品を未選定、対応確認をnullとして残しています。製品名も、実際に復元できたという事実も作っていません。

結果として35点検が「入力モデル上の解消」となり、標準方式の対応確認が3シナリオで確認待ちに移ります。情報不足は36から39へ増加します。これは意図した結果であり、独立性と復旧方式の対応をセットで検討する必要性を示します。

## 顧客説明時に残す判断事項

復元先が独立していても、復号・復元・業務再開が可能と確認できていなければ運用承認はできません。改善案の次の判断は、製品・版・ワークロード・復元先・鍵・認証断の対応確認、独立した復号/復元試験、隔離区画での検査・構成/権限レビュー、RTO/RPO実測、ログ保全と再接続承認です。

バックアップ管理面への到達、復旧点の削除耐性、鍵の使用可能性は別項目です。管理面に問題があることを、直ちにロック済みデータも削除できると説明しないでください。

## 再現する

```bash
python -m cleanroomcheck demo --out demo-output
```

`comparison.html` が比較結果、before/afterの各 `report.html` が根拠と証跡分類を含む点検結果です。質問票と検証計画のCSVは製品ヒアリングと次の試験計画に利用できます。
